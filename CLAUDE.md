# Drop Multivendor Water Delivery Platform — Developer Guide

Instructions and context for AI coding assistants working on the Drop platform.
Each sub-project carries its own `CLAUDE.md` with the rules specific to it; read
that one too before changing anything in that directory.

## Architecture & monorepo structure

Four client surfaces, **one** FastAPI backend and **one** database. There is no
second API and no separate admin datastore — a figure on the console and a figure
in a vendor's app cannot drift apart when they come from the same query.

- `BackendAPI/` — Python FastAPI backend, plus an ARQ worker in its own process.
- `drop-customer-app/` — Expo app for customers.
- `drop-rider-app/` — Expo app for delivery riders.
- `drop-vendor-app/` — Expo app for water vendors and their staff.
- `drop-admin/` — Next.js App Router operations console, deployed on Vercel.
- `docs/` — architecture, runbooks, deployment, audits. Start at `docs/README.md`.

## Coding conventions

### Backend (FastAPI / Python)
- Standard Python typing and Pydantic v2.
- Modular: `routes/`, `services/`, `models/`, `schemas/`, `jobs/`, `dependencies/`.
- `geoalchemy2` for PostGIS; H3 res-8 for bucketing before the exact pass.
- WebSockets live in `websocket_routes.py` and `order_service.py`, over Redis pub/sub.
- Background work is ARQ (`worker.py`), which runs as a **separate process**. `RUN_INLINE_WORKER=1` is for a single-process dev machine only — inside the API, every replica runs its own copy of the cron schedule.
- Contended rows (accepting an order, moving a wallet, settling bottles) are taken with `select(...).with_for_update()`. Sweeps use `FOR UPDATE ... SKIP LOCKED` and commit per item.

### Mobile apps (React Native / Expo)
- **Styling**: NativeWind. Dark mode is required on every screen.
- **State**: TanStack Query for server state, Zustand for client state.
- **Routing**: Expo Router (file-based).
- **Data fetching**: custom hooks over the app's API client (`useApiRequest()` / `apiFetch`). Never fetch inside a component, and never use raw `fetch` — three separate test suites fail the build if one reappears.
- **Errors**: surface the backend's own message through `Toast.error(..., errorMessage(err))`. Never show a raw status code, and never branch on the wording of a message — branch on `ApiError.type` or `.status`.

### Admin console (Next.js)
- `lib/api/server.ts` is `server-only`; importing it from a Client Component is a build error. Client components call a Server Action, which calls that module. The browser never holds an API token.
- Every destination is declared once in `components/shell/nav-config.ts`; a test fails the build if a `page.tsx` has no entry.
- Semantic tokens only (`bg-surface`, `text-muted`, `border-default`).

## Common tasks

### Backend
```bash
cd BackendAPI
source venv/bin/activate
docker compose -f docker-compose.dev.yml up -d   # Postgres 16 + PostGIS, port 5434
uvicorn main:app --reload
arq worker.WorkerSettings          # second terminal
pytest -q --ignore=tests/test_multi_store_integration.py
```

`tests/test_admin_e2e.py` connects to whatever `DATABASE_URL` names — it is the
one file in the suite that touches a real database. Pointed at a managed
provider, **every `pytest` run spends metered compute**; that is how the Neon
project reached its quota and took the deployed API down with it. Point it at
the local container. Full setup, and moving the deployed database to another
provider, is `docs/database-setup.md`.

### Expo apps
```bash
cd drop-rider-app                  # or vendor / customer
pnpm install
npx tsc --noEmit                   # before every push
pnpm start
```

### Admin console
```bash
cd drop-admin
pnpm install
pnpm dev                           # http://localhost:3000
pnpm typecheck && pnpm build
```

## Security & guardrails

Platform-wide invariants. Most are enforced by a test that parses the source and
fails the build, so breaking one is a CI failure rather than a production
incident.

- **Proof of delivery**: completing an order with `emptiesReceived < computedEmptiesExpected` requires a photo. **Do not bypass this check in a `catch` block** — a failed upload is a failed completion.
- **KYC**: riders stay blocked in `VerificationWall` until `kyc_status == "approved"` is *positively confirmed*. The gate fails closed; an errored status query is not permission.
- **Money is `Decimal`, never `float`**, from the database through the API to the string the client formats. On the frontend use `sumMoney()`, never `reduce((a,b) => a + Number(b))`.
- **Money reaches every client as a decimal *string*, and there is one converter each way.** `utils/money.py::money_str` on the way out, plus `MoneyField` / `OptionalMoneyField` for schema fields; `utils/money.ts` in each app and `lib/utils/format.ts` on the console on the way in. Two conventions ran side by side for a long time — the quote, the wallet balances shown to a rider and a vendor, the customer's payment history, and `order_snapshot`, which is the frozen record a delivery dispute is settled from weeks later, all left as JSON numbers. A money field annotated `float` on a schema is the quiet version of the same defect: there is no cast to grep for, because Pydantic does the coercion. `test_money_serialisation.py` walks both the schemas and every response dict in `routes/`, `services/` and `jobs/`, and `MONEY_FIELDS` in it is the specification.
- **Never re-derive an order total on a client.** `total_amount` is frozen on the order at creation. Four screens summed the component lines instead — and each omitted the bottle deposit and any settled balance, so the customer's card, the customer's detail screen and the vendor's copy of the same order all disagreed with the M-Pesa message.
- **`calculate_revenue_splits` takes and returns `Decimal`.** It used to take floats and return floats, and every caller wrapped the result straight back up in `Decimal(str(...))` — a float round trip in the middle of the one path that decides what a vendor, a rider and the platform are each owed.
- **A fatal render error is reported, in all three apps.** `ErrorBoundary.componentDidCatch` calls `captureError`; the boundary swallows the crash, so it is the only place that class of error is observable at all. The vendor app carried a `// TODO` there while Sentry was initialised and working beside it — on the surface where a broken screen costs a shop its orders. `test_crash_reporting.py` fails the build if any of the three stops reporting.
- **Every app's route table is enforced, not just the customer's.** `test_route_contract.py` runs over all three: every declared path must resolve against FastAPI, every declared entry must be called by a screen, no path may be built inline, and no app may grow a second table.
- **A console page checks the capability it needs before it renders.** `pageAccess()` reads that capability from `nav-config`, so the gate and the sidebar entry that hides it cannot disagree. This is courtesy, not access control — `require_admin(...)` is still the only check that decides anything — but a page that paints its heading and then shows "403 Forbidden" reads as a broken console, and the person reports an outage instead of asking for the capability.
- **One pricing path.** `services/pricing_service.py::compute_order_quote` is the only place an order total is computed. Never re-derive one on a client or in a second service.
- **Business values are rows**, not constants — 85 settings in `Platform_Settings`, edited from the console, live on the next quote. A figure that belongs to the business and sits in the source is a defect; four of the audit's fourteen findings were exactly that.
- **Changing a shipped default does not change a running platform.** A stored row outranks it, permanently and silently, and a row that merely materialised the *old* default is indistinguishable from a decision somebody made. Retiring a default therefore takes a migration that deletes rows still holding the superseded value — `b2f9c14e7a35` is the pattern, and `test_the_retirement_table_still_describes_todays_defaults` fires when a default in that table moves again. `retail_service_fee` sat at 12 on a platform whose source said 35, on a row left behind by a verification run.
- **Two push paths only**: `queue_push` before a commit, `dispatch_background` after. A bare `asyncio.create_task(send_push_message(...))` fails the build. **The rule is about the reference, not about pushes** — `asyncio` keeps only a *weak* reference to a task, so any detached work whose return value is discarded can be collected part-way through. `update_orders_payment_status_by_checkout_id` fired the post-payment rider dispatch that way: customer paid, order `unassigned`, no rider ever told, nothing logged, and likeliest under load because that is when GC pressure is highest.
- **A grant is claimed by proving you hold the mailbox it was sent to.** Staff and administrator access are both granted by email address, so "what is this caller's address?" is an authorisation decision — and Clerk lets anyone attach an *unverified* secondary address to their own account. `utils/clerk_identity.verified_email_for` is the one implementation: verified only, no `addresses[0]` fallback, failing closed on an unreadable verification shape. There were two private copies, neither checking verification; the vendor one handed over a store and the admin one handed over the console, which reads every customer record, every rider's national ID and the money. The admin API shares a Clerk instance with the three apps, so every customer holds a structurally valid token to try it with. `test_identity_binding.py` fails the build if a second copy appears.
- **Registration resolves a store by ownership, never by reachability.** `POST /api/vendor/register` upserts `business_name`, `phone_number` and `vendor_type`, and resolved through `get_vendor_by_clerk_id` — whose filter is `owned OR staffed`. A staff token therefore rewrote the *owner's* business, including the type that decides both the commission rate and the service radius. Never `scalar_one_or_none()` on either registration path: it raises `MultipleResultsFound` on an owner's second store, and `get_existing_vendor` backs the endpoint onboarding posts to.
- **Two columns decide whether someone may act on a store, and every access query reads both.** `revoke()` writes `revoked_at` and `is_active` together, so spread `*live_grant()` rather than checking one. Seven of eight queries checked `revoked_at` alone — including `staff_membership`, which backs `resolve_order_role` and `owns_entity`, i.e. the **websocket** path, so a deactivated member would have been refused over REST while still streaming the store's live orders. Roster queries (`list_staff`, `_get_member`) deliberately keep the looser filter, or a suspended member cannot be restored.
- **A suspension has to stop the work.** `get_verified_rider` refuses a suspended rider *before* it looks at KYC — the two are different statements, and a suspended rider sent to `VerificationWall` resubmits documents that were never the problem. Every rider search spreads `*dispatchable_rider()`; they filtered on `is_available`, which is the rider's *own* toggle, so a suspension was a switch its subject could flip back and only cash orders were refused. `is_suspended` reads `suspended_at` and deliberately not `is_active`, which is overloaded — `create_deliverer` defaults it `False`, so it also means "has not finished onboarding". And an administrator's decision is not the subject's to undo: `create_rider` and `create_vendor` both re-post ordinary onboarding forms, and both wrote standing flags unconditionally.
- **A customer sees a storefront, not the person who owns it.** `VendorStorefront`, never the owner's `owners_name`, `email`, `phone_number` or `preferred_payment_method` — that last being the store's **payout destination** despite the name. `POST /vendor_details_and_products` had no auth dependency at all and `GET /vendors` handed out every store id, so the two together were an owner-name-plus-phone-plus-till list for the whole vendor base. Every vendor discovery route is authenticated, and a test fails the build on either half.
- **Safaricom's spelling wins, and their idempotency key gets sent.** B2C's parameter is **`Occassion`**, two s's, in both their v3 request body and their parameter table — and Daraja discards a key it does not recognise, so the correct English spelling was the bug: the payout id had never once been attached to a disbursement, which is the field that ties an M-Pesa statement line back to a payout row. Same shape as `googleMapId`, one system further out. `B2C_OCCASION_KEY` names it so nobody "corrects" it back; the Reversal API is documented with the single-s spelling, and the two really are inconsistent with each other. Separately, `OriginatorConversationID` was not being sent at all — their table marks it required and describes it as the guard against **double disbursement**, and `500.002.1001` is the refusal it produces. Omitting it means the gateway cannot deduplicate, on the one money path where a repeat does not miscount something but pays a rider twice; `payout_id` is the natural key and must stay stable across a retry. `test_daraja_contract.py` asserts the wire body, not the code.
- **The Safaricom IP allow-list is measured against the Daraja you are actually calling.** `SAFARICOM_IP_RANGES` is a list of *production* addresses, so enforcing it against sandbox callbacks refuses every one — **after** a correct secret has already matched, silently from both ends, with the order stuck at `pending` and one log line as the only evidence. `is_safaricom_ip` reads `MPESA_BASE_URL`, never `ENV`, which is what lets a staging or pre-launch deployment run `ENV=production` — every fail-closed gate on, cron guarded, the callback secret genuinely enforced — while still pointed at sandbox. It is defence in depth either way and cannot stand alone: `ProxyHeadersMiddleware` trusts every forwarding host, so the shared secret is the guard.
- **Storage for an identity document fails closed.** `upload_file_to_s3` branched on the *credential* rather than the *environment*, so a production deploy with no AWS key took the development path: a rider's national ID written unencrypted to the container disk, and a **truthy** `/api/uploads/…` returned — which passed the KYC route's own `if not front_url` check. The submission reported success, `kyc_status` went to `pending`, and the file was unreachable immediately, because `/api/uploads` is not a mounted route and the disk is wiped on the next deploy anyway. Nobody could then be approved, so every rider sat in `VerificationWall` with nothing anywhere naming the cause. Money, KYC and cash gates fail closed here; this is one of them. `test_storage_fails_closed.py` also asserts no `/api/uploads` route exists, so the premise cannot rot.
- **An STK push names the endpoint that settles it, and no two kinds of payment share one.** `CallBackURL` is sent *in the request body* — there is no portal registration and nothing in Daraja decides it — so it is a per-caller choice, and it was a module-level `os.getenv("MPESA_CALLBACK_URL")` that both callers inherited. A `CheckoutRequestID` resolves against `Orders` for a checkout and against `WalletTransactions` for a top-up, so every wallet top-up's confirmation was delivered to `/api/cart/mpesa/callback`, which found no order and returned **400** — a retry instruction to Safaricom, not an acknowledgement. The customer's money left their phone, the transaction stayed `pending` for ever, and `handle_mpesa_topup_callback` — written, guarded, correct, reachable — had never once been called, because nothing had ever told Safaricom its address. `callback_url` is keyword-only and required on `initiate_stk_push` for exactly that reason: a default is what re-adopts one caller's endpoint for the next one. Resolve it with `order_callback_url()` / `topup_callback_url()`, which return `""` when unconfigured so the push is refused rather than collecting money with nowhere for the confirmation to land. `test_stk_callback_routing.py` fails the build on a call that omits the argument, on two callers sharing one URL expression, and on a declared path that no route serves. The residue is `reconcile-pending-topups`, which settles from an STK *query* — and a query carries no receipt and no amount, so it credits what was asked for and records the reconciliation rather than inventing a Safaricom reference.
- **Every M-Pesa callback arrives more than once, and answers "already done?" under a lock.** Safaricom retries until it gets a 200, and for order payments the client's `/confirm_payment` poll settles in parallel and usually wins — at which point `update_orders_payment_status_by_checkout_id` returns early, *before its own commit*, so anything the callback added is discarded. `checkout_request_id` is UNIQUE and is the idempotency key: record the audit row and commit it on its own, then guard the follow-up work (the confirmation email, the cart purge) on whether *this* call settled the order. The top-up, B2C and reversal handlers all filter on the state they are leaving and take the row `FOR UPDATE`.
- **Every mutating admin route records who did it.** `Admin_Audit_Log` exists because the environment variable it replaced made nothing attributable. Read-only POSTs are exempt by name — `/config/preview` takes a body because it prices a sample order, and persists nothing.
- **`action_url` is an Expo Router path**, always — `/(screens)/…`. It is read by the three apps and by nothing else. A console URL there is a silent dead link: the customer app's whitelist blocks it, the other two push an unmatched route. A test walks every `action_url=` in `services/`, `routes/` and `jobs/`.
- **A support reply fans out through `support_service._notify_requester`** and nowhere else. It writes the row, queues the push, and reaches a store's staff as well as its owner. Replies used to record and email without ever pushing — the one message somebody is actually waiting for was the only one that never interrupted them.
- **Never read `Vendor.staff_clerk_id` or `staff_push_token`.** Staff are `Vendor_Staff` rows with four capabilities.
- **Every order-scoped endpoint, REST and WebSocket, calls `authorise_order_access`.** Authenticating proves who is calling, not that they have anything to do with that order.
- **Never call a Google web service from a client.** The embedded keys are SDK-restricted and cannot; `routes/maps_routes.py` owns Directions, Places and Geocoding on the IP-restricted server key.
- **Personal data**: lists render masked values for every role. Revealing an identity document is an audited action requiring `pii.view` and a stated reason, presigned for 5 minutes, and rendered with a plain `<img>` — `next/image` would cache somebody's national ID on a server.
- **Moderated reviews are excluded from every public read** and from the target's rating, in the same transaction.
- **Every withdrawal path calls `settlement_service.assert_withdrawable`.** A wallet balance is not what is spendable — float promised to open cash orders is settled at delivery. Two paths existed and only one checked.
- **A withdrawal fee is waived on the amount withdrawn, never the balance held** (`settlement_service.fee_for`). Both apps measured the balance and told people to keep money in the wallet to earn a free withdrawal — a rule the platform does not implement and would not want, since it pays one M-Pesa tariff per disbursement. The minimum, fee and waiver all arrive from `wallet-summary`; none is ever a literal in an app.
- **`revert_order_side_effects` is the only way to cancel an order.** It undoes seven things; six call sites each remembering a different subset is how `commission_lost` went missing on vendor rejects.
- **Products are withdrawn (`deleted_at`), never deleted**, and every catalogue read carries `live_product()`. `Order_Items` references them and the bottle ledger reads their capacity.
- **A customer's deposit is a liability the platform can return.** `customer_bottle_service` moves `bottle_deposit_balance` and `bottles_held` together, never one alone. Both, and `debt_balance`, are on `BasicUser` — a column the customer cannot see is a balance they cannot check, and all three were maintained correctly while reaching nobody.
- **Every path that returns a deposit goes through `customer_bottle_service._return_bottles`** — the rider collection, the console's manual return and the dormancy conversion. It is the one implementation of what a bottle is worth back (the customer's own per-bottle average, not today's schedule), *and* it guarantees the `Bottle_Return_Requests` row the nightly reconciliation subtracts. A path that returns money without writing that row makes the book report permanent growing drift, indistinguishable from a real accrual bug.
- **A returned deposit buys water, not cash.** It lands as `wallet_balance` with `non_withdrawable_balance` raised to match; withdrawable is `wallet_balance − non_withdrawable_balance`, the same shape as a rider's committed cash float. Otherwise the deposit is a money-transfer service — pay KSH 300 by M-Pesa, hand the bottle back, withdraw KSH 300 to a different phone — and with the welcome discount against the deposit that round trip cleared a profit. Spending consumes the restricted part **first**; a withdrawal consumes **none** of it.
- **A handover needs two counts, and the timeout is asymmetric on purpose.** Rider-confirmed and customer-silent auto-settles at the rider's count: they attested to taking a physical asset and carry it on their own ledger. Customer-confirmed and rider-silent **never** auto-settles — a timer that pays a unilateral claim pays anybody who waits. Counts that differ are a dispute a human decides; never split the difference.
- **A returned bottle arrives somewhere.** `settle_return` writes a `DEPOSIT_RETURN` ledger entry against the destination store, so a bottle leaving the customer's count does not leave the platform's books while still physically existing.
- **Every charge in a quote is rendered as its own line.** `debt_settlement` sat in `total` with no line on the cart, so the customer paid an unexplained difference. `delivery_markup` is the one exception: platform margin inside the delivery fee, not a separate charge.
- **Every M-Pesa amount goes through `payment_service.whole_shillings`.** Daraja
  moves whole shillings; `int(amount)` truncates. The withdrawal fee is a
  settings row an administrator may set to 15.50, at which point a KSH 1,000
  withdrawal debited 1,000, recorded a fee of 15.50 and put **984** on the phone.
  It refuses rather than rounds — the caller has already decided what to debit.
- **A wallet movement records the balance row it came off** (`wallet_owner_id`).
  `user_id` is a Clerk id and one identity may own several stores with a
  `wallet_balance` each; callbacks arrive minutes later and re-resolved by clerk
  id with an unordered `.first()`, so a top-up into the second branch credited
  the first and a failed withdrawal from the second was refunded to the first.
  Resolve with `wallet_service._locked_wallet_owner`, never by clerk id.
- **Cash on delivery is gated in four places, and `services/cod_policy.py` is the only one that decides.** Checkout (`cart_routes`) asks whether this customer may pay cash at all; acceptance (`deliverer_service`) asks whether this rider may carry it, **before** the float check; completion demands a photo; a ten-minute sweep releases float from cash orders nobody delivered. The float check only ever asked *can this rider cover it* — a four-day-old account with a large balance passed every time, for any number of orders at once.
- **The checkout cap is the *platinum* ceiling, deliberately.** Capping at `cod_max_order_value_standard` would mean no order above it could ever exist, making `cod_max_order_value_platinum` unreachable. An order between the two is Platinum-only, and acceptance refuses everybody else by name.
- **A rider's drop reason is validated against the stage the order is in.** `deliverer_service` declared three lists — vendor-fault, rider-fault and post-pickup — and consulted only the first, so any string at all was accepted. A post-pickup drop could be recorded as `out_of_stock`, which cannot happen to an order already on the bike and counts against the store in every figure that reads `cancellation_reason`. Whose fault it was also decides whether the customer still gets their water: a shut store cancels, a rider's own problem unassigns and re-offers.
- **A name used and never imported is invisible until a user reaches the line.** `cancel_customer_order` called `func.count(...)` with `func` never imported; the module loaded, every test passed, and because the free-cancellation allowance defaults to **1**, a customer cancelling an order that had reached `preparing`, `ready` or `picked_up` got a 500 instead of a cancellation. `test_no_undefined_names.py` runs pyflakes over everything that serves a request and fails on an undefined name, a re-imported name, or a local computed and never read.
- **A vendor's cancellation never counts against a rider's completion rate.** Otherwise the gate punishes the riders working with the least reliable stores.
- **`services/vendor_availability.py` is the only thing that decides whether a store is trading.** `is_online` is one of five reasons a shop may not be — pause, offline, opening hours, suspension, and the platform-wide overrides — and it was the only one anything read. Worse, it was read by *nothing on the ordering path*: the vendor app shipped a swipe control wired to it, so a vendor could swipe their store closed, watch the toggle turn grey and keep receiving orders. `shift_start`/`shift_end` were in the same position since the first migration. Every customer-facing vendor read carries `vendor_service._annotated`, checkout and `create_order` both call `assert_store_accepting`, and a test fails the build if any module in `services/` or `routes/` re-derives the answer.
- **A store's own controls fail *open*.** An unreadable `paused_until` or `min_order_value` is treated as no pause and no minimum, not as an error: a shop's optional convenience setting must never be able to 500 a customer's checkout. The platform's own gates — money, KYC, cash — fail closed; these are the opposite case and the distinction is deliberate.
- **A pause expires; `is_online` does not.** The indefinite switch is the one people forget — tapped during a rush, and the store is dark until somebody notices the next morning. `resume-paused-stores` clears expired pauses and tells the store, but the state is already correct without it: `store_state` compares the expiry against the clock, so a worker that never ran cannot leave a shop shut.
- **Pausing is `manage_orders`; the terms of trade are owner-only.** Whoever has just run out of 20 L bottles at 11am is standing behind the counter, and a pause they cannot apply until they reach the owner arrives after the orders do. Whether the store takes cash at all, and its minimum order, sit with the payout account.
- **A closed store is marked, never hidden.** Filtering it out of discovery tells the customer looking for the shop they always use that it has left the platform, and costs a store that paused for twenty minutes its place in everybody's list rather than twenty minutes of orders.
- **An order's status changes through `apply_status_transition` and nowhere else.** `VALID_TRANSITIONS` used to be a table fifteen writers ignored and two consulted — and it described an *idealised* flow the platform does not have, so it contradicted the thirteen. A table nobody reads is dead code; a table that contradicts the code is documentation that lies, and the next person either believes it about their own feature or "fixes" the conforming paths to match. It now describes what happens, terminal is terminal, and nothing goes backwards.
- **Read `DispatchPolicy` through its accessors, never the dataclass defaults.** `RETAIL_MAX_DISTANCE_KM` is the shipped default; `retail_max_distance_km()` is the configured row. A direct read is invisible — right value, right type, passing tests — until an administrator moves the setting and the two halves of the platform disagree about the same rule. Discovery read the default while checkout read the row, so widening the radius delivered further without letting anybody *find* the store that had come into range.
- **No route group's index forwards into its own group, and `<Redirect>` is never unconditional.** Expo Router resolves a path *relative to the group the caller is already in*, so `/` from inside `(Auth)` resolved to `app/(Auth)/index.tsx` — which forwarded to the sign-in screen, which redirects to `/` once a session exists. A two-node cycle that never left the group, while `app/index.tsx` — the file that owns the decision and terminates — was never reached again. `<Redirect>` issues `router.replace()` from an effect on **every render**, not once per mount, so neither side settled and React threw "Maximum update depth exceeded" straight after a successful sign-in. `(Auth)/index.tsx` is deleted in all three apps and every caller names `/(Auth)/sign-in/screen`. Guarding the group index instead is *not* the fix: returning `null` when signed in stopped the loop and produced a blank screen, because that file was still what `/` resolved to. `test_navigation_redirects.py` reads `<Redirect>` targets only — `router.push` from a tap handler runs once and cannot cycle, and an earlier version of the rule failed on eleven legitimate ones.
- **The splash is a launch animation, so it plays once per process.** `useState(false)` in `app/index.tsx` gave a fresh `splashComplete` to every mount, and that route is remounted by every redirect to `/` — which the sign-in screen does the moment a session exists. So the full `SPLASH_DURATION_MS` (**ten seconds**) replayed *after* the user signed in, and only then did routing continue. `hasPlayedSplash` lives at module scope because that is exactly the lifetime "this app has launched" describes. The second half: a wait is not a launch. `readyToRoute === null` while the profile-status call is in flight used to fall back into the same `<AnimatedSplash>`; it gets an `ActivityIndicator` on the themed ground instead.
- **A screen's identity comes from its route parameter, and its content from its query — never from a copy of either.** `product-details/[id].tsx` mirrored the query into `useState` and rendered the mirror. Expo Router keeps **one component instance per route pattern** and swaps the parameters, so moving from product A to product B does not remount: the query key changed and `data` correctly went `undefined`, but the mirror did not, so the screen kept rendering A under B's id — and `add_to_cart` read its id from the path and sent **B**. A price the customer reads and an id the button sends have to be the same product. With B withdrawn (`deleted_at`, and products here are withdrawn rather than deleted, so **404 is a routine answer** — a favourite, a past order, a shared link, a notification's `action_url`) the copying effect never ran again and A stayed on screen permanently, offered for sale. Reproduced by deep-linking an id that has never existed: the page rendered "Alkaline 20L Refill, KSH 100.00, In Stock". The second half was that the render was `{!ProductLoaded ? <Skeleton/> : <Product/>}` with no error branch at all, so a 404 fell through to the skeleton and animated for ever — an endless loading state is a quieter bug than a crash, not a smaller one. `test_route_params.py` fails the build on a parameter recovered by slicing `usePathname()`, on a query copied into state, and on a record fetched by the parameter with nowhere to put a failure; a **terminal early return** on the record being absent satisfies the last one, an inline ternary falling back to the skeleton does not, because that is the defect. And the `any` was the cover: typing the screen from the query surfaced a nullable `vendor.lat` passed to a `number` parameter and the **seventh** copy of `Math.round((price - discount) * 100) / 100` — on the subtotal read immediately before *Buy Now* — after the other six had been removed.
- **A hook's `enabled` is the only thing that can stop a fetch; an early return cannot.** Hooks all run before a component may return, so `(screens)/_layout.tsx` guarding on `isLoaded` further down does nothing for the `useCart()` on its first line — the cart was requested before Clerk held a token and answered `403: Not authenticated` on every cold start. `useAuthReady()` is the gate.
- **Every socket the apps open carries `?token=`, derives its origin from `WS_BASE_URL`, watches for silence, and never stops retrying.** All four failures are silent from both ends: the socket never opens, or stops delivering while `readyState` still says `OPEN`, and the screen simply stops changing. The vendor's live-tracking map shipped without a token and so had never once shown a moving rider.
- **Every vendor self-service control is bounded by a settings row** (`storefront` group). Self-service with no ceiling is not self-service: a store setting a KSH 50,000 minimum has delisted itself while still appearing open and still ranking in search, which reads as the platform being broken rather than the shop being shut. **Vendors still do not set their own delivery fee or radius** — the rider is paid out of the delivery fee, so a store undercutting to win orders would be spending the rider's money.
- **The service radius is 2.5 km retail, 15 km wholesale, set by the platform, and nobody else states it.** One figure per vendor type — `retail_max_distance_km` / `wholesale_max_distance_km` — and it is *all* of: what discovery searches, what checkout enforces, what the rider search covers, and the circle each app draws. Read it through `DispatchPolicy`'s accessors; never write it in an app. `Vendor.delivery_radius` was a vendor-writable column that no dispatch path ever read, so the stepper wired to it changed no delivery — it only widened the circle on the vendor's own map and inflated the ETA the customer app quoted from the same column, to *every* customer of that store. The column is dropped (`c7d2e94a6f18`); `GET /storefront` reports the real figure to a store and `GET /rider/profile` reports it to a rider.
- **Both radii are `decimal` settings, not `int`.** The `int` coercer is `int(value)`, which truncates rather than refuses — 2.5 would have been stored as 2 in silence, on the number that decides which stores a customer can see at all.
- **A Postgres enum column is never `coalesce`d with a Python string.** Postgres refuses `COALESCE(vendor_business_type, varchar)` rather than choosing a result type, and the statement dies at execution: `DatatypeMismatchError`. A *comparison* is unaffected, because there the column anchors the literal's type — which is what made this invisible, since `coalesce(Vendor.vendor_type, "retail_refill") == "wholesale_b2b"` had one correct half and one fatal one in the same expression. It classified a store to pick its service radius, so `/api/search` and `/api/search/vendors` both answered **500** for every customer whose location was known, and 200 only for the one case no real customer is in — no coordinates, which never reaches the predicate. Name the NULL instead (`or_(col != x, col.is_(None))`): it keeps the branches exhaustive, keeps the literal typed by the column, and keeps the index. **Nothing in the backend suite touches a real database** — `tests/conftest.py` yields an `AsyncMock()` — so an error only Postgres raises is invisible to all 1,370 tests; `test_sql_type_safety.py` is the static stand-in, reflecting over the models so a column that becomes an enum later is covered without anybody remembering. The test that *did* cover this asserted `func.coalesce(Vendor.vendor_type` was present: it pinned a mechanism rather than the rule, so it failed on the fix exactly as loudly as on a regression. It now asserts the compiled SQL.
- **A read that serves `StorefrontState` has asked `vendor_availability`.** Its six fields default *permissively*, so a read that forgets to annotate does not omit the answer — it serves `store_state: "open"` for every store. `search_vendors_service` lives in `query_service` rather than `vendor_service` and was never annotated, so a paused shop read as open in search and closed on its own page: the two surfaces the mixin exists to keep in step. The guard now starts at the wire — every route handler naming a schema that inherits `StorefrontState`, discovered by subclass rather than listed — because the previous one enumerated seven functions in one module by name, and the eighth was in another.
- **`Vendor.preferred_payment_method` is the vendor's *payout destination***, despite the name — `MPESA_TILL`, a paybill, a bank account, written by the app's payout settings screen. It has nothing to do with which payment methods the store accepts; that is `accepts_cash`. Conflating them would point a customer's payment method at the vendor's bank details.
- **A CAC never silently blends what the platform can measure with what it cannot see.** `welcome_discount` is real acquisition spend and is on every order; posters, a branded boda, ads and referrals are not in this database and never will be. `admin_growth_service` returns `measured`, `entered` and `blended` separately with `has_entered_spend`, because a CAC built from the measured half alone is precise, confident, and typically wrong by an order of magnitude **in the direction that makes acquisition look cheap** — and somebody then spends against it.
- **Spend in a month that acquired nobody is counted and named, never dropped.** Summing entered spend per cohort is the obvious implementation and it discards exactly the months that matter, since a month with no acquisitions has no cohort. `unattributed_spend` reports it on its own. The arithmetic that hides it is the arithmetic that flatters.
- **A cohort is a customer's first *delivered* order, and the `MIN()` runs over all history.** An account that never received water was not acquired; and a first-delivery date computed inside the window would re-acquire a two-year customer into this month's cohort, inventing new customers out of loyal ones.
- **Cohort contribution is `platform_net`, never re-derived.** It is frozen on the order at creation, so moving a commission today cannot restate what a cohort earned last March.
- **Nothing in the growth service is projected.** `realised_per_customer` is named as realised. An LTV extrapolated from four months of data is a guess wearing a number's clothes, and it is the number people raise budgets against. Median payback counts only cohorts that have actually paid back — averaging in the young ones reports a payback period faster than any cohort has ever achieved.
- **Signing out has to end the session on the *device*.** Each app clears the push token for **its own** `app_type` — the endpoint defaults to `customer`, and a rider omitting it cleared nothing, committed, and got a `200`, so the rider who signed out and the next one to sign in both kept receiving the first one's delivery offers on a shared handset. `clearPushToken()` runs *before* `signOut()` (the endpoint is authenticated); everything else is `useSessionCleanup`, mounted in the root layout rather than in the handlers, because a session also ends on any 401 and on a revocation nobody tapped. Anything persisted outside the query cache — the customer's `asyncStoragePersister`, the vendor's `activeStoreId` — has to be wiped there too.
- **A control with only an icon in it carries an `accessibilityLabel`.** React Native names a touchable from its `<Text>` children, so text buttons are free and icon-only ones announce as "button" and nothing else. `PressableScale` already supplies the role in all three apps, so the label is the missing half.
- **Never coalesce a missing capability with `?? 0`** in the console. `undefined` means "not yours"; `0` means "nothing waiting". A badge that renders the first as the second leaks the size of a table the caller cannot see.
- **Lazy loading is not a strategy here — all 38 relationships are `lazy="raise_on_sql"`.** Under asyncio an unloaded attribute already failed; it failed as `MissingGreenlet`, naming a greenlet rather than the relationship. The setting names the attribute instead. What it does *not* do is move the failure into the test run: `tests/conftest.py` yields an `AsyncMock()` and **no test in this suite touches a real database**, so nothing here exercises ORM loading at all. `test_relationship_loading.py` is what finds the defect — it walks response schema → route → service and requires an eager load for every relationship Pydantic will serialise. It found two, both of which worked by accident: `get_deliverer_orders` never loaded `Order.deliverer` and got away with it because the rider was already in the session's identity map, and `get_trip_radar_orders` got away with it because an `unassigned` order usually has a null `deliverer_id` — until a re-offered one does not. Also beware a bare `backref="name"`: `lazy=` governs only the forward direction, so the reverse side keeps the library default with nothing at the call site to show it.
- **A cohort is written when it becomes true, not derived when it is read.** `Customer_First_Delivery` replaces a `MIN()` over every delivered order that has ever existed — unbounded *on purpose*, which is also why it could only get slower and why no index could help. `services/customer_cohort_service.py` holds the one definition; the migration backfills from it, the delivery path writes through it, and a nightly sweep reconciles against it. The write is **monotonic, not first-wins**: orders do not reach `delivered` in `created_at` order, so an order placed in January and disputed until March delivers *after* one placed in February, and first-wins would leave that customer in the wrong cohort permanently, contradicted by an order in the same table. And "every delivery path remembers to call the hook" is the assumption that lost `commission_lost` on vendor rejects, so it is not an assumption: `test_customer_cohorts.py` **discovers** every call that can move an order to `delivered` — classifying each `apply_status_transition` by the status it passes, treating an unresolvable one as a delivery, and exempting a variable only where a status whitelist in the same function proves it cannot deliver — and requires `record_acquisition` beside it. A missing call site is a build failure, not a number somebody has to be watching. The nightly sweep stays for the residue CI cannot see (a delivery reversed after the fact, a hand-corrected row, a restore), and escalates what it corrects to Sentry rather than logging it into a cron output nobody tails.
- **A rate limit counts an account, not an address.** `core/rate_limit.py` resolves the *verified* Clerk subject and keys on that; the address is the fallback for callers who have not proved anything. Safaricom and Airtel put mobile subscribers behind carrier-grade NAT, so thousands of customers reach the API from a handful of IPs — keyed on the address, the global limit was one budget shared by every Safaricom data customer using the app at once, the busiest throttling the quietest, with 429s that look random and reproduce perfectly from a single office IP while never explaining themselves. The subject is verified rather than read, because a JWT is base64 JSON and an unverified key hands every attacker unlimited fresh buckets. `RateLimitKeyMiddleware` must be registered **after** `SlowAPIMiddleware` — Starlette runs middleware outermost-first in reverse order, so later registration means earlier execution, and swapping the two silently reverts every limit to the IP.
- **A photograph is not a document.** `utils/s3_utils.public_asset_url` serves product images, store logos and avatars from a stable, content-addressed URL; `generate_presigned_url` stays for identity documents, delivery proof and dispute evidence. A presigned URL embeds its own expiry in the signature, so the same photo has a *different URL in every response* — and every image cache in the stack keys on the URL, so a changing URL means every client re-downloads every image on every refresh. A twenty-item catalogue is ~800 KB re-fetched per refresh on metered Kenyan mobile data. `test_scale_guards.py` fails the build in **both** directions: presigning a photograph is a bandwidth defect, and serving a document from a public URL is a data-protection incident.
- **A `304` is a promise the body is still valid, so a body with an expiry never gets an ETag.** `core/conditional.py` adds `ETag` to safe reads and answers `304` when the client already holds the data — the largest single win for users on limited or unstable data, because a request that cannot fail large is a request that mostly succeeds. It skips any body containing `X-Amz-Signature`: telling a client its cached copy is good, when part of that copy expires in fifteen minutes, surfaces later as broken images with no error anywhere. It is registered **before** GZip so it hashes the uncompressed body; hashing the compressed one would give the same rows two tags depending on `Accept-Encoding`.
- **`ST_DWithin` as a filter, `ST_Distance` only to sort.** The first is index-assisted against the GiST index on the location column; comparing a computed `ST_Distance` forces a distance per candidate row before anything can be discarded. Three of the four dispatch searches did the latter — including the two that run first, on every order. Search results are also bounded (`RADAR_FANOUT_LIMIT`): an unbounded radar pushed to every available rider in the ring, and past a couple of dozen the rest only ever get a notification for an order that is already claimed.
- **A timeout is a function of the connection and the request, never a literal.** `API/netBudget.ts` in each app reads the live NetInfo state and the request kind. A flat 15 s is a broadband number: on a congested cell, a request that would have completed at 25 s was aborted, retried twice and reported as a failure — three quarters of a minute of spinner and three uploads of the same body over metered data, manufacturing the hang the timeout existed to prevent. An upload carrying a photograph gets the longest budget, because aborting one at 90% at a customer's gate is strictly worse than waiting.
- **Money stays a decimal string all the way to the handset's disk.** The rule did not stop at the network boundary and neither does the enforcement: the rider's offline SQLite declared `total_amount REAL`, which is the copy read when the rider is offline and therefore cannot check it against anything. Money columns on-device are `TEXT`.
- **Three faces, and a weight utility always names one.** Karla for body and UI, Fredoka for headings and capped at **600**, JetBrains Mono for figures and identifiers. In the apps that means `font-sans-bold`, never `font-bold`: a bare weight utility sets `fontWeight` and names no family, so React Native renders the *system* font and thickens it — Roboto on one handset, San Francisco on another, and bold enough in review to look intended. There is no `font-synthesis-weight` and no variable-weight axis in React Native, so a registered per-weight face is the only mechanism there is; `fontWeight` in a `StyleSheet` is the same defect one layer down. Fredoka's heavier weights read as a children's brand on a platform that moves people's money, which is why there is no `font-heading-bold` and why the console pairs the cap with `font-synthesis-weight: none` — otherwise `font-bold` on an `<h2>` is a browser-thickened 600 and the cap buys nothing.
- **React Native has no cascade, so the body face is attached per element.** `components/ui/Text.tsx` in each app wraps `Text` and `TextInput` and supplies `font-sans` when the class string names no family; nothing imports either from `react-native` directly. It resolves at render time on purpose — `<Text className={labelStyle}>` is a real pattern here, and no find-and-replace can see which branch built that string. **Figures stay in Karla**, headings take Fredoka: a screen, sheet or modal title, an entity's name, the brand. A balance, a total or a count is not a heading, on the console (`Stat` renders `<p>`, deliberately) or in an app.
- **`test_typography.py` is the specification** and fails the build on any of it: a bare weight utility, a `Text` imported from `react-native`, a `fontFamily` naming a face `_layout.tsx` never registered, Fredoka above 600, a resurrected Inter, or a self-referential `--font-mono`. That last one is why the console's JetBrains variable is `--font-jetbrains-mono`: `--font-mono` is Tailwind v4's own theme token, and a custom property defined in terms of itself is a cycle CSS discards at computed-value time, leaving the page with no monospace font at all and nothing to grep for. `--font-sans` pointed at an undefined `--font-inter` for exactly this reason — the console had never once rendered in its intended face, and every fallback chain was quietly doing the work.
- **One declaration per wire shape, per app.** The customer app carried **two** `Order` interfaces and **two** `Product`s — one pair in `types/models.ts`, one pair inside the hooks that fetch them — and a screen got whichever it happened to import. They had drifted eighteen fields apart: the hook's `Order` had the whole money breakdown and the coordinates, the shared one had `customer_id` and `updated_at` the hook's lacked, and the hook's `Product` typed **`price` and `discount` as `number`** on the two figures a shelf label is built from. This is the second-table defect one layer up, and resolving a path against the server cannot catch it — both copies typecheck, and the copy nobody imports typechecks best of all. `types/models.ts` is the single declaration; the hooks re-export from it.
- **A discounted price is `discountedPrice(price, discount)`, and a badge is `discountPercent`.** Six screens wrote `Math.round((price - discount) * 100) / 100` inline on two decimal strings, then hand-prefixed `KSH ` rather than going through `formatMoney` — a float subtraction and the exact `* 100` round trip `utils/money.ts` exists to prevent, on the number a customer reads before deciding to buy. `{discount > 0 && …}` on the same field is the companion defect the guide already forbids. A store nobody had rated crashed the map's vendor card outright: `Array(Math.round(null))` is `Array(NaN)`, which throws.
- **`googleMapId`, not `mapId`.** Every map screen in all three apps passed a Google Cloud map id under a prop `react-native-maps` does not have — six screens, one silently dropped prop, and cloud styling has never once been applied on any of them. A misspelt prop on a native view produces no warning in either direction; it is the JSX equivalent of a field the server does not send.
- **An unused import is a name in scope, not clutter.** `routes/vendor_management_routes.py` imported `get_vendor_by_clerk_id` — the function this guide says a route must never call — with nothing calling it, sitting at the top of the file for the next person to reach for; and `or_` sat unused in `auth_dependencies`, `auth_routes` and `vendor_service`, the residue of the `owned OR staffed` filters that were deliberately narrowed. An import left behind after a rule is tightened is the shortest path back to the old behaviour. `test_no_undefined_names.py` now fails the build on all four pyflakes categories, not three.
- **The console has no native browser dialogs.** `window.confirm` and `window.prompt` removed an administrator and revealed a customer's contact details and a rider's identity documents. They ignore the theme, so light system chrome lands over a dark console at the moment somebody is deciding whether to trust the screen; they block the tab synchronously, so React, every in-flight request and `IdleTimeout` are frozen behind one; they are **suppressible**, so a browser told to prevent further dialogs returns `false`/`null` showing nothing, and the button reads as broken; and `prompt` cannot validate, which matters because two of the three collect a *reason written to `Admin_Audit_Log` before the presigned URLs are minted*, against endpoints that refuse an empty one. `components/ui/ConfirmDialog.tsx` is the one replacement — themed on both grounds, focus-trapped behind its own `aria-modal`, Escape and backdrop cancel, and the confirm button stays disabled until an audited reason has actually been typed.

## Tests, and the build that runs them

Four suites, one command each, and `.github/workflows/ci.yml` runs all of them
on every push and pull request:

| | |
|---|---|
| `BackendAPI` | `pytest -q --ignore=tests/test_multi_store_integration.py` |
| each app | `pnpm test` (jest + `jest-expo`), and `npx tsc --noEmit` |
| `drop-admin` | `pnpm typecheck && pnpm build` |

This file says in many places that a rule "fails the build". For a long time
there was no build to fail: the guard tests that parse the apps' source ran only
when somebody typed `pytest`, and the three apps had **no test files at all** —
the customer app carried a full jest setup and a `test` script with nothing to
run, the other two carried testing-library as a dangling dependency with no
runner. That is the same assumption this platform refuses everywhere else, and
it is why `record_acquisition` is a build failure rather than a runbook note.

The apps' own suites cover what a static guard cannot reach — behaviour. Money
arithmetic against the cases a float gets wrong; the API client's timeout, HTTPS
enforcement and error normalisation; the paging de-duplication; the rider's
offline queue refusing to delete a completed delivery; the order-status groups
covering every status the backend can return. They run in about two seconds each
because the logic they test has no React in it.

**Domain rules belong outside hooks.** The customer's status groups lived in
`hooks/queries/useOrders`, so asserting that a filter covers `preparing` pulled
in Clerk, React Query and the whole API client — forty-five seconds and a live
handle for a pure assertion about strings. They are in `constants/orderStatus.ts`
now, which is where the vendor app has always kept its own.

## Migrations

The repository head, `e6b2c8d40f17`, is **gated on purpose**: it drops the legacy
single-staff columns and refuses to run without `ALLOW_STAFF_COLUMN_DROP=true`.
Routine deploys should target `f7e3b91c8d24`, the last revision before it. The
expand/contract sequence is in the gated migration's own docstring.

A new revision goes **before** the gated drop, never after it — anything parented
on `e6b2c8d40f17` could only ever run on a deploy that had already accepted the
column drop.

**The chain cannot build this database.** Sixty-five revisions, two bases, and
not one creates `Vendors`, `Users`, `Orders` or `Products` — those tables
predate Alembic, so every revision *alters* a schema no revision *creates* and
`alembic upgrade head` against an empty database dies on the first `ALTER
TABLE`. PostGIS is in the same position: 44 spatial calls depend on it and no
migration creates it, because it was enabled by hand on the first database and
never written down. `scripts/bootstrap_database.py` is the path for an empty
one — extensions, `Base.metadata.create_all`, then stamp — and it refuses if a
migration history already exists, because there `create_all` is exactly what
`db/session.py` warns against.

That premise only holds while `Base.metadata` *is* the schema. Four models —
`Bottle_Rejection_Tickets`, `Customer_First_Delivery`, `Deliverer_Vendors`,
`failed_webhooks` — existed as files that `models/__init__.py` never imported,
so they were reachable only by the services importing them directly and nothing
ever failed. A database built from the models came out four tables short, and
every guard that reflects over the models had been skipping them, including
`test_sql_type_safety.py` — three of the four carry enum columns, which is the
blind spot that let `COALESCE(vendor_business_type, varchar)` reach customers.
`test_model_registry.py` reads `models/__init__.py` **statically**: `conftest`
imports `main`, which reaches those modules anyway, so a runtime check of
`Base.metadata` passes on the very commit it exists to catch.
